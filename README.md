## 一、文言锦囊 — AI 驱动的古文实词学习小程序

**2025.11 – 至今｜独立开发｜已上线运营，累计服务 600+ 用户**

> **微信搜索「文言锦囊」即可直接体验。**

面向中学生的古文实词学习微信小程序，覆盖 150 个中考高频实词，融合生成式 AI 构建"学 — 测 — 练 — 复习"的完整闭环，支持学生 / 教师双角色。后端为自建 Java 17 + Spring Boot 3 + MySQL 服务（JWT 鉴权、Flyway 迁移、Nginx + HTTPS），AI 能力构建在智谱 GLM API 之上。从产品设计、前后端开发、AI 集成、自动化测试、CI/CD 到上线运营，全部由我一人完成。

### ① 线上运行证明

### ③ AI 能力：智能讲解与"小古文记词"

这是产品的差异化核心。左为 AI 智能讲解，按【字源演变】【典型用法】【易错点】【记忆口诀】四段结构化返回，并以 SSE 流式输出实现"边生成边显示"；右为自研的**小古文记词**——用户选定 4–8 个要背的实词与文风后，模型流式生成一段包含这些词的文言短文，并逐词精确标注义项，把孤立的词义放回有故事性的语境里记忆。生成后还会**逐词校验目标实词是否真的被用上**，不合格则不予采信。

![AI 讲解与小古文记词](images/wyjn-ai.jpg)

**成本控制**是这个功能能长期存活的前提。AI 调用采用三层机制：同一个词的讲解结果**全局复用**（他人首次查看直接命中缓存）、**用户级快照**（同一用户重复查看免费且不消耗配额）、**分功能每日额度**与会员覆写；并配套 token 用量计量、成本估算与近似余额看板。

## 二、Weave — 多 Agent 旅行攻略整合 App

**2026.9 – 至今｜个人项目，独立设计与开发**

### ① 产品与特色

很多人刷小红书时截了一堆攻略，到了目的地却用不上：截图里的建议重复、说法不一、地名写法五花八门，还夹着过期信息和广告。Weave 让用户把这些截图丢进某次旅行，系统自动读图、去重、识别冲突，挂到 AI 生成的行程骨架上，得到一份随投喂不断完善、能照着走的个人行程。

它的特色是**"让模型只摘录、不编造"**：每条建议都能追溯到原图或网页出处，精确时间、票价这类最容易被模型编出来的信息，只能来自原文或实时查询。技术栈为 TypeScript + Expo / React Native（一份代码出 iOS 和 Web），大模型使用 Claude 与通义千问（含多模态），按任务路由。

![Weave 界面：旅行列表、待办、行程、收集](images/weave-screens.jpg)

### ② 多 Agent 系统

整套 AI 能力由一个编排 Agent 和 5 个专职 Agent 协作完成：

| Agent | 职责 |
|---|---|
| **编排 Agent** | 判断这次输入是新截图、一句话备注还是"第三天轻松点"这类改行程请求，拆成子任务、按依赖关系分派，最后汇总成"待确认的提案" |
| **读图 Agent** | 多模态模型读截图，抽取建议并附原文出处；长截图切段读取 |
| **地点 Agent** | 地名归一：精确 / 别名、相似度 ≥ 0.9、0.7–0.9 交给用户确认三档，连锁店拆成品牌加分店，坚持"宁可漏合并，不可误合并" |
| **整合 Agent** | 语义去重（相似度召回，0.85 以上直接合并，中间地带交给 LLM 终审）和冲突识别（按时段、季节、同行人、交通等 6 个维度判断适用条件是否互斥，再给出带权重、可解释的倾向） |
| **行程 Agent** | 生成行程骨架；把自然语言的修改请求转成结构化的改动提案 |
| **校验 Agent** | 所有要写进行程的内容最后过一遍：出处覆盖率低于 0.8 的丢弃、数字只能来自原文、schema 禁止的字段不得出现 |

一次完整的流程是这样的：用户投喂几张截图 → 编排 Agent 并行派给读图 Agent → 抽出的建议交地点 Agent 归一 → 整合 Agent 与行程里已有内容去重、标出冲突 → 校验 Agent 把关 → 编排 Agent 汇总成"新建议 N 条、可合并 M 条、冲突 K 条"，**用户点"用上"才写进行程**。模型给建议，人做决定。

### ③ Agent Harness

大模型本身只会读写文字，harness 是包在模型外面的运行框架：告诉模型有哪些工具可以用，模型发出调用时由 harness 真正去执行，再把结果喂回模型，循环到给出答案。Weave 的 harness 是自研的统一运行时：

- **工具注册表**：地图 / POI 检索、天气、网页搜索，以及内部的读图、地名匹配、合并终审、行程读写，都用 zod 定义入参和出参；Agent 只能调用注册过的工具，参数先校验再执行，外部 API 有超时、缓存和限流
- **执行循环与预算**：每个 Agent 有最大步数、token 预算和超时，超预算时强制收尾、返回已有结果
- **结构化输出与回喂重试**：模型输出先过 zod 和确定性规则检查，不合格就把具体失败原因喂回去重试；能用代码修的小问题直接修，省一次调用
- **降级**：任何一个 Agent 或工具调用失败，都回退到规则路径（例如整合时退回按文字相似度合并），主流程不中断
- **多模型路由**：读图走视觉模型，终审和改动提案走文本模型，Claude 与通义千问可按任务切换
- **全链路 trace**：每一步记录 Agent、工具、提示词版本、模型、耗时和 token，出问题可以完整回放

### ④ 工程化

- 领域逻辑写成与界面解耦的纯函数，**48 个单元测试全部通过**，覆盖去重、冲突识别、地名归一和行程改动
- 用固定样例集做**离线回归评测**：改提示词或换模型后跑一遍，对比去重、冲突识别和出处覆盖率是否退化
- 整个项目约 1.7 万行 TypeScript，配有 4 份设计文档，记录每个阈值和设计取舍

> **小结**：Weave 关心的不是"让模型多说点"，而是"让模型说的每句话都有出处"。多 Agent 负责把复杂任务拆清楚，harness 负责让每一次模型调用都可控、可降级、可回放。

## 三、TIMO — 面向医学深度研究的开源轻量大模型

**清华大学智能产业研究院（AIR）TIMO 项目团队｜工程组负责人｜长期参与，持续跟进**

### ① 项目是做什么的

医院算力条件不均、数据又不能出院，通用大模型在医学场景里很难真正落地。TIMO（TIMO-OSS-Search-Preview）是清华 AIR 研发的医学深度研究模型，目标是让**可以私有部署的轻量模型**也具备医学深度研究能力。拿到一道复杂的医学问题后，它会像研究员一样一轮轮地"思考 → 联网检索 → 阅读指南和文献原文 → 再推理"，最后给出可核验的循证答案。

项目包括三条主线：证据驱动的训练数据合成（知识图谱自动出题、复杂问题轨迹蒸馏、多级拒绝采样）、模型与检索执行框架（harness）的协同迭代，以及面向学术汇报和开源发布的展示平台。模型提供 4B 和 27B 两档。

![TIMO 实时研究界面：对话、研究过程、资料库](images/timo-live.png)

### ② 工程组做什么，我做什么

项目团队分算法组和工程组：算法组负责数据合成、模型训练与论文；工程组负责把模型的研究能力做成**可演示、可交付的系统**，包括 Demo 展示平台、轨迹数据管线以及与实时推理服务的对接，并跟着模型和 harness 的每一版迭代持续更新。

我是工程组负责人，负责工程架构、任务拆分和代码评审，并与算法组对接。具体工作包括：

- **一套事件协议，两种数据源**：回放（读离线轨迹）和实时（SSE 推送）本来要写两套界面。我设计了前后端共用的事件流协议并写成文档，制定"只加字段不改名、不兼容改动升级 schema 版本"的规则。之后两种模式共用同一套 React 前端，切换数据源不用改界面代码，实时后端也能并行开发。
- **轨迹转换管线**：用 Python 把 6 个医学基准共 1,034 道题的智能体原始轨迹转换成前端事件数据。过程中发现模型一次打开多个网页时被当成了一个网址（涉及 2,417 次调用），修复后研究过程才对得上；另外接入 NCBI 与 OpenAlex 接口，为引用文献补全期刊、被引次数和 DOI，并按每秒 10 次限流。
- **回放引擎与资料库**：实现回放播放引擎（1–8 倍速、按轮跳转、打字机效果、"紧凑 / 真实"两种节奏、快捷键与深链）、可搜索的资料库和中英双语界面。联调时定位到实时版切换英文失败的根因：大模型安全审核把医学用药内容误判为违规，而只要一条翻译失败就会拖垮整页。
- 带领工程组合并了 17 个 PR，个人提交约 4,500 行代码。

![资料库：研究过程中收集和阅读过的文献](images/timo-library.jpg)

### ③ 项目成果

取得 6 个医学基准共 1,034 道难题上 48.5%（27B）和 40.4%（4B）的总体准确率，分别超过闭卷作答的 Claude-Opus-5（42.9%）和 GPT-6-astra（36.1%），并领先同类开源医学模型；借助 harness 与模型协同迭代，将总体准确率较初代提升 4.55 个百分点；从 22 万余候选题中筛选出约 3,500 条高质量训练轨迹；在 2026 第二届北京清华医学人工智能论坛（Beijing-Tsinghua Health AI Summit）以口头汇报和海报形式发布成果，参加 CCL 2026（第二十五届中国计算语言学大会），在 GitHub 与 Hugging Face 开源 4B / 27B 模型，并交付展示平台支撑现场演示与开源发布。

> 模型训练与论文由算法组完成，以上准确率为团队成果；本页只展示界面截图，不涉及代码与评测原题。

> **小结**：在一个研究型团队里做工程，我练的是让工程节奏跟上模型迭代：模型和 harness 每更新一版，展示平台都要能接得住。

## 四、无缝不至 — 云边协同道路裂缝检测系统

**2023.5 – 2025.6｜团队负责人兼算法开发｜重庆大学云帆科技团队创始人**
国家自然科学基金项目｜重庆市大学生创新训练项目优秀结题

面向道路裂缝检测行业长期依赖人工巡检、效率低且漏检率高的现状，自主研发云边协同的道路质量智能检测软硬件平台：车载边缘计算盒子在行驶过程中完成路面裂缝的实时推理与告警，微信小程序端支持用户上传图片视频至云端按需深度分析，两端共用同一套检测模型，兼顾巡检车辆的实时性与普通用户的可及性。

### ① 算法：面向微小裂缝的检测架构定制

微小裂缝是道路检测的经典难题。我独立完成数据集构建与模型研发：采集约 **5,000 张**原始裂缝图像，经仿射变换等数据增强扩充至 **2 万余张**样本，覆盖不同路面材质、光照与天气条件。针对微小裂缝易漏检的核心难题对 YOLO 检测架构做深度定制——引入自适应锚框优化以匹配裂缝细长的几何特征，重新设计 FPN+PAN 特征融合结构解决多尺度特征丢失，并以 GIoU 损失函数替换标准边界框回归损失提升定位精度。最终模型在复杂环境干扰下的综合识别率达 **97.8%**，并完成裂缝类型的分类识别。

## 五、Lumie — Live2D AI 情感陪伴应用

**2026.4 – 至今｜AI 工程 & 移动端开发，二人团队**

> **访问 [lumie.love](https://lumie.love) 可直接体验。**

面向情感陪伴赛道的移动端 AI 应用：Live2D 虚拟形象的表情随对话内容实时联动，接入火山引擎豆包端到端实时语音，并由长期记忆系统支撑跨天、跨话题的连续关系。前后端解耦的双仓库架构（移动端 Vue 3 + Vite + Capacitor + Live2D；服务端 Hono + Postgres + Neo4j + 管理后台），团队以多分支 + PR 流程协作。

### ① Live2D 角色与对话

角色形象、表情与口型随对话情绪实时变化，支持多角色与场景背景切换。我承接了 AI 输出落到界面的最后一环——从模型回复中剥离内部控制标记、将情绪词映射为虚拟形象的实时表情，配合流式渲染让回答逐字浮现。

![Live2D 对话](images/lumie-chat.jpg)

### ② 长期记忆：知识图谱与图增强检索

纯向量检索的记忆有三件够不着的事：多跳关联（"她提过的那个总加班的朋友"）、矛盾消解（三个月前说喜欢猫、上周说被抓了很怕猫）、时间锚点（"去年的今天你刚答辩"）。我设计并实现了基于 Neo4j 的记忆图谱与图增强检索管线：

- **抽取**：正则预分类器先判断这一轮是否值得抽取，命中后由 LLM 做结构化抽取，把开放域对话蒸馏为「人物 / 事件 / 偏好 / 情绪」实体-关系三元组，幂等入图
- **存储**：向量索引直接建在图节点上，图与向量共用一份存储，避免双写漂移
- **检索**：先从当前话轮抽取实体，再以**图邻域多跳召回**与**向量语义召回**双路并行，按相似度、重要度、时间衰减与跳数距离加权融合排序，装配为记忆注入块
- **矛盾消解**：新事实与旧事实冲突时建立 `SUPERSEDES` 关系而非覆盖——当前回答用最新状态，但"你以前是喜欢猫的"这层关系纵深被保留下来

### ③ 记忆的产品化呈现

我主导了记忆模块的信息架构重构：把后端存下的一条条零散记忆记录，按"你眼中的她 / 她眼中的你"重新组织成四板块的故事化叙述，让用户打开看到的不是一张数据库列表，而是一段正在生长的关系。

![记忆页](images/lumie-memory.jpg)

### ④ 提示词治理与离线评测

我把产品整套 LLM 提示层从散落在 12 余个后端服务的硬编码字符串，收敛为数据库驱动、含 **21 个结构化槽位**（人格、对话风格、流式与 JSON 输出契约、记忆抽取与注入、Cypher 生成、主动搭话、实时语音风格）的可在线编辑注册表：变量插值、逐槽位变量声明、代码内置默认文本兜底——任何被改坏的编辑都回退到原始提示词，而非向模型注入一段空的 system message。提示词迭代由此从"改代码 + 重新部署"变成"后台改一行"。

![管理后台在线编辑提示词](images/lumie-prompts.jpg)

在此之上，我自建了约 750 行的**离线评测工具链**，把提示词写作从凭感觉变成可对照比较：一个脚本为每个槽位批量生成风格各异的候选；另一个把候选用统一的真实输入 fixture 填好后**实际调用模型跑一遍**，分两种模式——生成式（填好的提示词即请求，模型输出即成品）与行为式（把候选注入为 system prompt，再以顶撞 / 求助 / 随口透露等脚本化话术探测其反应）——每个槽位单独配置采样温度与 token 预算，并让线上正在使用的提示词在完全相同的输入上跑一遍作为对照，全部汇入一份并排报告作为选型依据。

心情记录、关系里程碑、商城与钱包等模块，构建陪伴的"成长感"。
